## Friction Points

### F1: COMPONENT tag rejected 'tsa-throughput' value

- **Step:** 6d (TSA throughput)
- **Severity:** Low
- **What happened:** `ALTER TASK ... SET TAG ... COMPONENT = 'tsa-throughput'` failed because the COMPONENT tag (created in base-setup) only permits ALLOWED_VALUES `etl, analytics, realtime, backfill, properties`.
- **Resolution:** Used `COMPONENT = 'etl'` for the TSA tasks.
- **Recommendation:** Either add `tsa` to the COMPONENT tag ALLOWED_VALUES in base-setup (`sql-pipeline-infra.md` Step 2), or update tsa-throughput reference SQL to use an existing allowed value (`etl`). Prefer the latter to avoid changing the tag contract.

### F2: Tag/predecessor ordering races in sub-skill SQL

- **Step:** 6b (ADS-B), 6e (Derived analytics)
- **Severity:** Low
- **What happened:** Several `ALTER ... SET TAG` statements and one `CREATE TASK ... AFTER <predecessor>` (TASK_REFRESH_ANALYTICS) executed before their target object/predecessor existed, due to parallel statement dispatch.
- **Resolution:** Re-ran the failed statements after the target objects were created; all succeeded.
- **Recommendation:** Reference files should keep each object's CREATE immediately followed by its tag ALTER (already mostly true), and ensure CREATE TASK predecessor ordering is strictly sequential. Executors must run one statement per call in file order (which this run did) — the residual races came from intra-call parallelism in the sub-agents.

### F3: TASK_ENRICH_ADSB failed — FLIGHT_SCHEDULE stub missing FLIGHT_KEY (FIXED in source)

- **Step:** 7/8 (Task DAG)
- **Severity:** Medium
- **What happened:** With Aviationstack skipped, `FLIGHT_SCHEDULE` is created as a stub by derived-analytics (`01-adsb-data-local.md`). The stub omitted `FLIGHT_KEY` and `AIRCRAFT_REGISTRATION`, which `PROC_ENRICH_ADSB_WITH_SCHEDULE` (its `sched` CTE) references. The proc failed to compile (`invalid identifier 'FLIGHT_KEY'`), so `TASK_ENRICH_ADSB` FAILED — which would also skip its downstream `TASK_REFRESH_DERIVED` → `TASK_REFRESH_ANALYTICS` on each scheduled run. (DTs still auto-refresh on their own TARGET_LAG, so data flow was not fully blocked.)
- **Resolution:** (1) **Source fix (new-deployment-first):** updated the `FLIGHT_SCHEDULE` stub in `derived-analytics/references/01-adsb-data-local.md` to the canonical schema (added `FLIGHT_KEY`, `AIRCRAFT_REGISTRATION`, `DEPARTURE_DELAY`, `ARRIVAL_DELAY`, `IS_CODESHARE`) plus `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` guards for upgrade safety. (2) **Live fix:** ran the same `ADD COLUMN IF NOT EXISTS` on `AIRPORT_SAN.PUBLIC.FLIGHT_SCHEDULE`. Verified `PROC_ENRICH_ADSB_WITH_SCHEDULE(1)` now runs (source_rows=79, merge_rows=79). Source edit not committed (no-auto-commit policy) — pending user.
- **Recommendation:** Keep the stub schema in sync with the canonical `FLIGHT_SCHEDULE` produced by the flight-schedules MERGE proc (`flight-schedules/references/02-procedures.md`). Add a cross-ref eval that diffs the stub columns against the columns the enrichment proc selects from `FLIGHT_SCHEDULE`.
