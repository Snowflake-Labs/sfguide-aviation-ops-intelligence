# React Dashboard via Snowflake App Runtime

Deploy the React 18 + Express dashboard (`dashboard-react/`) with **Snowflake App
Runtime** — the managed runtime that replaces the manual SPCS pipeline (Docker,
image repo, compute pool, EAI, version scripts). This is the **default** React
deploy path; the manual SPCS path (see SKILL.md "React Dashboard (SPCS)") is
retained as a fallback while App Runtime is in public preview.

App Runtime builds remotely, packages an immutable version, creates/upgrades an
**Application Service**, and returns a stable HTTPS URL (Snowflake SSO).

## Prerequisites

| Requirement | Notes |
|-------------|-------|
| Snowflake CLI **≥ 3.19** | `snow app setup` does not exist in 3.16. `snow app --help` must list `setup`, `deploy`, `validate`, `bundle`, `events`, `teardown`. |
| Paid Snowflake account | App Runtime is not available on trial accounts. |
| Node.js 22+ (local) | For local `npm run dev` / build only. |
| At least one `AIRPORT_*` database | From `aviation-installer`. The app discovers them via `SHOW DATABASES LIKE 'AIRPORT_%'`. |

## Destination & sharing

- **Shared (recommended):** deploy into a standard database (`SNOWFLAKE_APPS`) so
  the app can be shared to other roles. Create the objects once:
  ```sql
  CREATE DATABASE IF NOT EXISTS SNOWFLAKE_APPS
    COMMENT = '{"origin":"sf_sit-is-aviation","name":"oss-aviation-dashboard","version":{"major":1,"minor":0},"attributes":{"is_quickstart":1,"source":"app"}}';
  CREATE SCHEMA IF NOT EXISTS SNOWFLAKE_APPS.PUBLIC
    COMMENT = '{"origin":"sf_sit-is-aviation","name":"oss-aviation-dashboard","version":{"major":1,"minor":0},"attributes":{"is_quickstart":1,"source":"app"}}';
  CREATE WAREHOUSE IF NOT EXISTS SNOWFLAKE_APPS_QUERY_WH
    WAREHOUSE_SIZE='XSMALL' AUTO_SUSPEND=60 AUTO_RESUME=TRUE INITIALLY_SUSPENDED=TRUE
    COMMENT = '{"origin":"sf_sit-is-aviation","name":"oss-aviation-dashboard","version":{"major":1,"minor":0},"attributes":{"is_quickstart":1,"source":"app"}}';
  ```
  (Or run Snowsight **Account → Apps → App Development Setup** once as an admin to
  set these as account defaults.)
- **Personal DB:** without setup, `snow app setup` targets `USER$<name>` — fine for
  build/test, but apps there **cannot** be granted to other roles.

## Manifest files

Two files live in `dashboard-react/`:

### `app.yml` (build manifest — committed)
```yaml
install:
  commands:
    - [ npm, ci, "--include=dev" ]   # MUST include dev: builder sets NODE_ENV=production
build:
  commands:
    - [ npm, run, build ]            # tsc -b && vite build  -> dist/
    - [ npm, run, "build:server" ]   # tsc server -> dist-server/
    - [ npm, prune, "--omit=dev" ]   # strip dev deps; keep runtime deps only
# NO `artifacts:` section — let the builder package the whole working dir.
run:
  command: [ node, dist-server/index.js ]
profile:
  icon: public/snowflake_h3.png
  label: Aviation Ops Dashboard
  description: Real-time airport operations analytics (ADS-B, gates, runways, TSA throughput).
```

### `snowflake.yml` (deploy config — generated by `snow app setup`)
Point the identifier at the shared DB and warehouse:
```yaml
entities:
  aviation_dashboard:
    type: snowflake-app
    identifier: { name: AVIATION_DASHBOARD, database: SNOWFLAKE_APPS, schema: PUBLIC }
    query_warehouse: SNOWFLAKE_APPS_QUERY_WH
    code_workspace: SNOWFLAKE_APPS.PUBLIC.AVIATION_DASHBOARD_CODE
    # artifacts.ignore excludes node_modules, dist, dist-server, .git, and the
    # manual-SPCS fallback files (Dockerfile.runtime, aviation_dashboard_service.yaml,
    # image-versions.env, .dockerignore*, scripts) from the source upload.
```

## Two critical gotchas (both cause silent build/run failures)

1. **`npm ci --include=dev` is required.** The remote builder runs with
   `NODE_ENV=production`, so a plain `npm ci` skips devDependencies and the build
   dies with `sh: tsc: not found` (typescript + vite are devDependencies).
2. **Do NOT add an `app.yml` `artifacts:` section.** It rewrites output paths via
   `dest` and breaks the layout — a non-`.` dest double-nests (e.g.
   `dist-server/dist-server/index.js` → `Cannot find module .../dist-server/index.js`)
   and `dest: "."` flattens by basename (destroys `node_modules` and `dist/assets`).
   Omitting `artifacts` makes the builder package the whole post-build working
   directory with correct relative paths (`dist/`, `dist-server/`, `node_modules/`,
   `package.json`). This is what the bundled Next.js template does.

> `snowflake.yml.artifacts` (source upload globs/ignore) is a **different** thing
> from `app.yml.artifacts` (built-file packaging). Keep the former, omit the latter.

## Deploy

```bash
cd dashboard-react
snow app setup --app-name aviation_dashboard -c <conn>   # generates snowflake.yml (first time)
# edit snowflake.yml identifier -> SNOWFLAKE_APPS / PUBLIC / SNOWFLAKE_APPS_QUERY_WH
snow app validate -c <conn>
snow app deploy   -c <conn>                              # upload -> remote build -> service
```

The deploy CLI may exit with `Endpoints provisioning in progress... check back in a
few minutes` / `Upgrade failed` even when the build succeeded — this is a **wait
timeout, not a failure**. Verify the real state with the SQL below; the service
usually reaches RUNNING shortly after.

## Verify

```sql
SHOW APPLICATION SERVICES LIKE 'AVIATION_DASHBOARD' IN SCHEMA SNOWFLAKE_APPS.PUBLIC
  ->> SELECT "name","status","is_upgrading",
             PARSE_JSON("source"):version::string AS ver, "url" FROM $1;
-- status RUNNING + is_upgrading FALSE = healthy. Container logs:
SELECT SYSTEM$GET_APPLICATION_SERVICE_LOGS('SNOWFLAKE_APPS.PUBLIC.AVIATION_DASHBOARD');
-- healthy startup ends with: "Aviation dashboard SPCS on :8080"
```
Build-job logs (when a build FAILS): the deploy output prints a
`SPCS_APP_BUILDER_JOB_*!SPCS_GET_LOGS()` table function — query it for the npm/tsc error.

Open: `snow app open --print-only -c <conn>` (URL uses Snowflake SSO).

## Data access (owner's rights)

Queries run as the service **owner role** (owner's rights). If the owner role is
ACCOUNTADMIN (or otherwise has access to the `AIRPORT_*` databases + query
warehouse), no extra grants are needed. For a least-privilege owner role, grant:
```sql
GRANT USAGE ON DATABASE AIRPORT_SAN TO ROLE <owner_role>;
GRANT USAGE ON SCHEMA AIRPORT_SAN.PUBLIC TO ROLE <owner_role>;
GRANT SELECT ON ALL TABLES IN SCHEMA AIRPORT_SAN.PUBLIC TO ROLE <owner_role>;
GRANT SELECT ON ALL VIEWS  IN SCHEMA AIRPORT_SAN.PUBLIC TO ROLE <owner_role>;
GRANT USAGE ON WAREHOUSE SNOWFLAKE_APPS_QUERY_WH TO ROLE <owner_role>;
```
For per-user data isolation use caller's rights (`querySnowflake(sql,{callersRights:true})`)
plus `GRANT CALLER ...`. The aviation dashboard is a shared read-only view, so
owner's rights is the default.

## Share with other roles

```sql
GRANT USAGE ON DATABASE SNOWFLAKE_APPS TO ROLE <role>;
GRANT USAGE ON SCHEMA SNOWFLAKE_APPS.PUBLIC TO ROLE <role>;
GRANT USAGE ON APPLICATION SERVICE SNOWFLAKE_APPS.PUBLIC.AVIATION_DASHBOARD TO ROLE <role>;
```
(`OPERATE` to suspend/resume/upgrade, `MONITOR` for logs.) Apps in a personal DB
cannot be shared.

## No external egress under App Runtime

The managed Application Service cannot bind an External Access Integration, so the
server cannot proxy outbound requests. The carto basemap is therefore loaded
**client-side** directly from the CDN (`src/shared/MapView.tsx` →
`https://a.basemaps.cartocdn.com/light_all/{z}/{x}/{y}@2x.png`); the old
`/api/tiles` Express proxy is removed. Keep any future external calls on the client.

## Iterate / rollback

- Redeploy: re-run `snow app deploy` — each deploy is a new immutable version and
  upgrades the running service in place; the URL is stable.
- Logs: `snow app events -c <conn>` (or `SYSTEM$GET_APPLICATION_SERVICE_LOGS`).

## Cleanup

```bash
snow app teardown -c <conn>   # drops the Application Service + workspace/code files
```
```sql
-- or by hand:
DROP APPLICATION SERVICE IF EXISTS SNOWFLAKE_APPS.PUBLIC.AVIATION_DASHBOARD;
DROP ARTIFACT REPOSITORY IF EXISTS SNOWFLAKE_APPS.PUBLIC.AVIATION_DASHBOARD_REPO;
-- SNOWFLAKE_APPS DB / SNOWFLAKE_APPS_QUERY_WH are shared infra; drop only if unused.
```
> Application Services may not carry a COMMENT tag, so `aviation-cleanup` discovers
> them by name (`AVIATION_DASHBOARD`) and the `AVIATION_DASHBOARD_REPO` artifact repo.
